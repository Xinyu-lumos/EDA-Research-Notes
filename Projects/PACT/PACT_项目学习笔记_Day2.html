02先分清调用中的角色

MCP（Model Context Protocol）在本项目中提供工具调用协议。客户端把“工具名 + 参数”发给本机 Python 服务端，服务端调用实际工具，最后返回结果。这里的默认连接使用 stdio，即进程标准输入/输出；无需先启动一个 HTTP 服务。

记住：MCP 是调用通道；工具后端负责实际执行。

层次在项目中做什么从哪里读
策略与技能选择动作、决定何时调用工具。LLM 通常经策略与技能间接驱动执行。stages.py、skills/
客户端维护两个会话，处理锁、超时、结果与后端状态。mcp_client.py · L269
服务端声明工具的参数格式，再按工具名分发请求。vivado_mcp_server.py · L7683；server.py · L89
实际工具Vivado 执行 Tcl；RapidWright 通过 Python/Java 接口访问设计。run_tcl_command()、rapidwright_tools.py

工具目录和执行逻辑要分开读

list_tools() 中的 Tool(name, description, inputSchema) 描述工具名、参数和类型；call_tool(name, arguments) 才是真正分发执行的位置。例如，Vivado 的 open_checkpoint 声明必需参数 dcp_path，处理分支随后生成对应 Tcl 命令。

读源码时先问“这个工具收哪些参数”，再问“这些参数最终怎样被使用”。不要把一大段工具描述当成实现。

03启动：先连接，再初始化，再加载

MCPClient.start_servers() 用当前 Python 解释器启动两个服务器脚本；工作目录设置为本次运行目录，而脚本路径从仓库位置计算。它先连接 RapidWright MCP，再连接 Vivado MCP，分别建立 ClientSession 并调用 initialize()。

记住：会话初始化完成，只说明调用通道已经建立。

记住：工具准备和 DCP 加载是后续步骤，不由 MCP 握手自动完成。

两个后端的准备方式不同

Vivado 侧的 ensure_vivado() 会在需要执行 Tcl、且进程不存在时调用 start_vivado()，通过 pexpect.spawn() 启动 vivado -mode tcl 并等待提示符。RapidWright 侧的 initialize_rapidwright() 配置运行环境后导入 rapidwright，由包启动 JVM。

这意味着看到日志“Both MCP servers connected”后，仍不能推断某份 DCP 已经加载。你需要继续找 open_checkpoint 或 read_checkpoint 的调用与成功响应。

一个细节：stdout 有用途stdio 是协议通道，不能混入任意日志。RapidWright 服务端会把 Java/JVM 的文件描述符输出重定向到日志，并保留 Python 的协议输出通道。这解释了 rapidwright.log 与 rapidwright-mcp.log 为什么分开。

源码：mcp_client.py · L319；vivado_mcp_server.py · L423；rapidwright_tools.py · L1023；server.py · L1629

04跟一次 Vivado 时序查询

用 report_timing_summary 做例子。假设客户端已连接、Vivado 已打开目标 DCP，调用点可以写成下面的形式。它是讲解片段，不是独立可运行脚本：

report = await mcp.call_vivado(
    "report_timing_summary",   # 服务端登记的工具名
    {},                       # 本次没有显式工具参数
    timeout=300.0,             # 客户端等待上限
)

记住：服务端把工具调用转成 Tcl：report_timing_summary -return_string。

记住：返回的是报告文本，WNS 等字段仍需后续解析。

  1. 客户端串行调用。call_vivado() 先获取 _vivado_lock，再由 _call_vivado_unlocked() 使用 asyncio.wait_for() 等待会话的 call_tool()。
  2. 服务端找到分支。call_tool() 匹配 report_timing_summary。源码先发一个 puts {timing_summary_start} 清理残留输出，再执行 report_timing_summary -return_string。
  3. 与 Vivado 交互。run_tcl_command() 用 sendline() 发送命令，等待 Vivado 提示符，从 proc.before 取输出，并移除命令回显。
  4. 客户端统一返回。_extract_tool_response() 提取文本并检查错误，成功时返回字符串。集中测量层再解析报告、结合路由与约束检查形成候选测量结果。
为什么有锁一个 Vivado 会话持有当前设计，并通过同一条交互通道接收命令。锁使单次调用串行化，避免两条命令交错；它不自动把任意多个调用变成一整段不可打断的事务。

源码：mcp_client.py · L582；vivado_mcp_server.py · L9352；vivado_mcp_server.py · L529；mcp_client.py · L202

05RapidWright：先证明自己读对了设计

RapidWright 服务端同样有 list_tools() 和 call_tool()，但分发后进入 rapidwright_tools.py 中的 Python 函数。例如 read_checkpoint 最终调用 Java 的 Design.readCheckpoint(...)，把对象保存在服务端的 _current_design 中。

代理经常需要对“某个候选”做只读探查。此时 call_exact_rapidwright_probe() 会在同一把锁内完成“对齐设计 → 调用探查”，防止中途被别的调用切换了设计。

记住：设计级探查需要代理提供候选身份；纯器件查询可以不加载 DCP。

记住：两个后端各有内存状态，修改不会自动同步。

身份绑定到底检查什么

客户端核对候选文件路径与实际 SHA-256；已有缓存身份与目标一致时可以复用，否则调用 read_checkpoint。服务端加载前后核对文件哈希，并在响应中返回 design_sha256。客户端再核对这个值，避免文件已改变或两端读取了不同字节。

直接切换 DCP 或调用可能修改设计的工具，会清除客户端旧的设计身份缓存。普通 call_rw() 本身并不保证自动加载正确候选；精确候选探查应关注专用封装。

交接还有一个实际细节

open_rapidwright_dcp_in_vivado() 会先查 foo.dcp.tcl，再查旧式 foo.tcl；若存在就通过 Vivado 的 run_tcl 执行 source，否则直接 open_checkpoint。这是读取代码时需要留意的交接辅助函数，不表示所有路径都经过它。

源码：mcp_client.py · L700；mcp_client.py · L792；server.py · L1240；rapidwright_tools.py · L1213；base.py · L516

06把调用串起来：phys_opt 技能

现在沿第 1 天见过的 PhysOptSkill 走一遍。假设策略选择 Explore 预设，技能从固定预设表得到 {"directive": "Explore"}；服务端据此拼成 phys_opt_design -directive Explore。

# 核心调用的教学化摘录；省略预算、日志和异常处理。
result = await mcp.call_vivado("phys_opt_design", mcp_args,
                               timeout=self._tool_timeout_s(params))
after_wns = await mcp.get_wns()
route_report = await mcp.call_vivado("report_route_status", {}, timeout=120.0)
# 只有技能内路由检查通过后，才执行下面的写出。
await mcp.call_vivado("write_checkpoint",
                     {"dcp_path": str(output_dcp.resolve()), "force": True},
                     timeout=self._tool_timeout_s(params))
  1. 先执行固定预设。技能校验预设和参数，调用 phys_opt_design，并收集可能解释“没有变化”的 WARNING。
  2. 再做技能内检查。读取 WNS 与 route status；如果设计未完整布线，返回失败结果。
  3. 保存可交接文件。写出 phys_opt_Explore.dcp，构造含文件路径、摘要与测量字段的 SkillResult。
  4. 回到代理的集中测量。技能成功只表示产出候选。代理仍需对规范化保存的候选重新测量，才能决定是否进入候选图并晋级。
理解这两个工具名的作用phys_opt_design 改变当前内存设计；write_checkpoint 把它保存为文件。缺少写出步骤，后续阶段就没有这次修改对应的候选 DCP 可供重开。

源码：phys_opt.py · L120；vivado_mcp_server.py · L9697；measurement.py · L145

07失败、超时和日志怎么读

跨进程调用成功返回，并不保证工具执行成功。两个服务端可能把错误包装成普通文本结果：Vivado 返回以 Error: 开头的文本，RapidWright 返回含 error 字段的 JSON 文本。因此客户端还会检查内容，发现错误就抛出 MCPToolError。

结果形态客户端的处理学习时的判断
isError=True在 _extract_tool_response() 中拒绝。协议/工具层明确报告错误。
{"error": ...} 或错误行扫描响应内容，抛出 MCPToolError。不要直接把字符串当成成功数据。
合法的空文本可能正常返回空字符串。某些 Tcl 命令本就不输出结果。
结构上不适用已识别的此类错误按 not_applicable 记录。与服务器坏了不是一回事；异常仍向上传递。
通信通道关闭提示进程与内存设计状态已丢失，要求显式恢复。失败命令不会被客户端自动重放。

两个 timeout，控制两层等待

call_vivado(..., timeout=...) 控制客户端等待 MCP 响应的时间；arguments["timeout"] 由服务端读取，用来控制 Tcl 命令等待。这两个参数不自动互相传递，默认值也可能不同。

# 参数示例：只用来说明两层 timeout 的位置。
await mcp.call_vivado(
    "report_timing_summary",
    {"timeout": 120},  # 服务端传给 Tcl 执行等待
    timeout=150,       # 客户端等待整个 MCP 调用
)

不要由“客户端停止等待”推断 Tcl 已停止。当前 run_tcl_command() 在自己捕获 pexpect.TIMEOUT 时会清理所属 Vivado 进程，并清空设计打开状态；客户端超时是另一条路径。

记住：重启和恢复检查点，不等于自动重试那条失败的修改命令。

restart_vivado() 在指定恢复文件时先验证路径和可选哈希；再在锁内请求重启。若通信本身不可用，它可重建 Vivado MCP 连接，RapidWright 会话仍保留。最后打开指定的恢复 DCP。

遇到的问题先看哪份日志寻找什么
某条调用失败或耗时很长代理日志中的 [VIV] / [RW]工具名、耗时、TIMED OUT 或 returned error。
Vivado 工具分发 / Tcl 失败vivado-mcp.log、vivado.log服务端分支、执行命令和 Vivado 输出。
需要追踪 Tcl 记录vivado.jouVivado 的命令记录，结合日志阅读。
RapidWright 初始化或 Java 出错rapidwright-mcp.log、rapidwright.logPython/MCP 层与 Java/JVM 层分别排查。

日志文件名对应非 debug 默认路径。源码：mcp_client.py · L165；mcp_client.py · L474；vivado_mcp_server.py · L529

  2. 10 分钟：跟踪候选身份。在精确探查辅助函数中找出“复用设计”“重新加载”“哈希不一致”三条路径，解释每条路径什么时候发生。

自测 1：日志显示两个 MCP 都连接成功，可以直接查设计吗？

不能只凭这条日志判断。还要准备工具运行环境，并确认目标 DCP 已加载；纯器件查询是无需设计的例外。

自测 2：RapidWright 改了一个 cell，Vivado 会立即看到吗？

不会。两个后端各有设计状态，需要通过写出 DCP、在 Vivado 中加载交接产物来同步。涉及配套 Tcl 的路径还应使用相应加载方式。

自测 3：MCP 返回字符串，为什么客户端仍可能抛异常？

字符串可能是工具错误，如 Error: 开头的文本或带 error 字段的 JSON。客户端会检查响应内容，不能只看传输是否返回。

自测 4：把客户端 timeout 改成 600，就把服务端 Tcl 超时也改了吗？

没有。客户端 timeout 与工具 arguments 中的 timeout 是两层参数。需要分别看客户端等待和服务端具体分支。

自测 5：为什么精确探查把加载与查询放在同一把锁内？

为了避免“加载了候选 A，查询前却被另一个调用切换为 B”。只对单次调用加锁，不足以保护这两个步骤之间的设计身份。

09把今天的内容接回总流程

今天你应该能说清：代理通过 MCPClient 调用本机工具服务；服务端把请求转成实际设计操作；两个后端各自维护设计状态，用 DCP 与身份检查把结果交回优化闭环。

第 3 天继续研究报告怎样变成可用证据：从 Vivado 文本报告进入解析和特征提取，怎样构造当前候选的证据快照，再支持动作菜单。入口会转向 collect_current_design()、features.py 与 stages.py。

复习时只看这五个入口MCPClient.start_servers() → call_vivado() → 服务端 call_tool() → run_tcl_command()；再对照 call_exact_rapidwright_probe()，理解 RapidWright 对设计身份的额外要求。

本课依据当前本地源码静态审阅，未执行 Vivado/RapidWright 端到端实验。函数名与文中源码行号用于定位本快照；后续代码修改可能使行号变化。
