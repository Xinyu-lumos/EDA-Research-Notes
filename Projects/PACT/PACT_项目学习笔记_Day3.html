01今天：把工具返回变成决策依据

第 2 天，我们跟着一次请求到达 Vivado，再带着结果返回。今天继续向前：工具返回的一段文本或 JSON，怎样成为能比较的数字、能追溯的证据，以及当前候选真正可以选择的动作？

报告说了什么

区分原始报告、解析字段和归一化特征，能手算一组关键指标。

结论根据什么

知道采样、缺失值和快照身份如何限制一条结论的适用范围。

最后能做什么

分清模型分析、可选菜单与执行绑定，理解参数从哪里来。

记住：这是阅读地图；菜单准备也可能发生在观测收集阶段。

今日验收能解释两个问题：为什么“布线主导比例为 0”不一定说明没有布线瓶颈？为什么模型认为某个动作很好，也不能任意修改它的参数？

02第一步：把报告解析成有名字的字段

入口是 collect_current_design()。它对当前打开的设计收集只读遥测，组装成 analysis 字典。你可以把这个字典看作“这一轮观测记录”，其中既有结果，也有工具是否可用的信息。

观测来源进入 analysis 的内容读的时候注意
集中测量 / 时序查询baseline_wns、clock_period、timing_summary有集中测量结果时优先使用；此处 baseline_wns 指本轮收集的测量，不必然是最初根候选。
时序路径 profiletiming_profile：路径数、布线占比、逻辑层数等工具返回的 JSON 被解码成结构化数据。
资源报告utilization：LUT、FF 等用量通过 report_utilization 返回文本，再调用解析器。
高扇出 / 结构探查fanout_nets、能力信息、拥塞、复制结构、carry 和硬宏级联不是每种探查都保证成功；同时记录可用性。

从最容易的一行开始

下面是教学用的资源报告行。解析器按竖线切列，去掉数字中的逗号，再识别 CLB LUTs 这一资源名。

| CLB LUTs | 1,200 | 0 | 4,800 | 25.00 |

记住：解析负责识别字段；它不会自动解释设计为什么慢。

这里“1200”回答用了多少 LUT，“25.0%”回答占可用资源的多少。后面的特征提取才会把时序、资源和路径结构组合起来。

源码：agent.py · L1599；parsers.py · L81。行号对应本次本地源码。

03第二步：用一个算例理解特征

extract_features(analysis) 产生 DesignFeatures。它把不同来源的字段整理为稳定的数值接口。先使用一组人为构造的教学数据：时钟周期 5 ns，WNS −1 ns；采样 4 条路径，其中 3 条被判为布线主导，平均布线占比为 70%。

记住：这是项目特征计算方式；单个归一化值不能解释全部时序问题。

特征本例计算应该怎样读
closure_ratio−1 / 5 = −0.20无量纲；未满足量相当于周期的 20%。
achieved_period_ns5 − (−1) = 6 ns项目根据周期和 WNS 推导的周期指标。
baseline_fmax_mhz1000 / 6 ≈ 166.67 MHz由上面的周期推导；不是独立扫频实测结果。
route_dominated_ratio3 / 4 = 0.75样本路径中，布线主导路径的比例；范围 0–1。
avg_route_pct给定为 70.0路径布线占比的平均值；百分数口径 0–100。
critical_lut_stage_ratioLUT6:6、FDRE:2 → 6 / 8 = 0.75logic_histogram 中 LUT 前缀原语计数占总计数的比例。

最容易混淆的两个“布线比例”

若 4 条路径的布线占比分别是 80%、75%、70%、55%，平均值是 70%。当前 profile 代码把单条路径的 route_pct ≥ 65 计为布线主导，因此 3 条达标，布线主导路径比例是 75%。一个平均每条路径里的占比，另一个统计符合条件的路径数量。

阅读数字时先补齐单位avg_route_pct = 70 表示 70%；route_dominated_ratio = 0.75 表示 75%。不要直接比较 70 和 0.75 的大小，也不要把这两项都写成“布线占比”。

源码：features.py · L33；features.py · L111；features.py · L144；timing_profile.py · L159。行号对应本次本地源码。

04先停一下：哪些结论还不能下

特征是观测的摘要。读懂它，还要知道“观察了多少”“有没有观察到”和“是否重复计算”。这三件事比背下字段名更重要。

① 样本不是整个设计

当前配置的 profile_num_paths: 40 和 fanout_num_paths: 50 是请求采样数量。它们不代表设计只有这些路径，也不保证工具实际返回同样多的路径。profile 保留请求/返回数量及 sample_may_be_censored 等信息；对比数据时要连同采样范围一起读。

② 缺失不是测得为零

_route_ratio() 在 path_count ≤ 0 时返回 0.0。因此同一个 0，可能表示“有样本且没有布线主导路径”，也可能只是“没有可计算的路径”。需要结合路径数量和 _telemetry_availability 判断。

一个很具体的误读不能看到 route_dominated_ratio = 0 就断言“应该优先优化逻辑”。如果 profile 根本缺失，这个结论没有相应的路径证据。

_telemetry_complete 的判断也很具体：存在 profile、其中路径数为正，且 utilization 非空。它不表示每个探查都成功，更不表示候选设计已通过合法性检查。

③ 同一路径可能经过多个高扇出网

假设网 A 覆盖路径 {1, 2, 3}，网 B 覆盖 {2, 3, 4}。覆盖并集只有 4 条，不能把 3 + 3 写成 6 条。特征代码优先用当前 path_samples 匹配可操作目标；缺少足够样本时采用保守的单网最大覆盖回退，避免直接叠加重叠计数。

源码：config.yaml · L205；agent.py · L1822；features.py · L225；timing_profile.py · L148。行号对应本次本地源码。

05第三步：把本轮证据固定下来

报告属于某一份 DCP 的某一次观测。后续切换了候选或重新采集后，即使文档名相同，证据也未必相同。publish_report_snapshot() 用候选身份、文件哈希和观测轮次，把这层关系保存下来。

记住：“固定”依靠内容哈希与读取校验，不是给文件设置只读属性。

存储层保存什么为什么分开
私有观测记录深拷贝 analysis，移除 _report_documents 后保存到 telemetry/<DCP SHA>/epoch_XXXXXX.json 并计算哈希。保留精确观测，供内部追溯和绑定使用。
研究文档集合重建 operator_extraction_profile.json、measurement_summary.json、authorized_action_menu.json 等。给模型受控的结构化视图；并非直接把全部原始 .rpt 原样暴露。
快照清单记录文档名称、字节数、行数、文档哈希以及快照身份。限定可搜索内容，并检测读取对象是否发生变化。

三个身份字段，各自回答一个问题

  • candidate_id：属于候选图里的哪个候选？
  • artifact_sha256：对应 DCP 的哪一份具体字节内容？
  • telemetry_epoch：属于哪一轮观测？

snapshot_id 由快照内容与身份信息形成。加载和读取时会核对哈希，所以修改文件之后不能继续把它当作原来的可信快照使用。

源码：agent.py · L2030；operator_extract.py · L687；corpus.py · L71；corpus.py · L155。行号对应本次本地源码。

06第四步：让分析能回到具体证据

Report 阶段通过 grep_reports 检索快照文档。它不是让模型任意搜索磁盘：文件必须在清单内，调用次数、返回字节、上下文和匹配数量都受限制。

记住：引用验证证明来源可追溯；分析是否正确仍要看推理。

例如 report:measurement_summary.json:12 表达“report 范围下，这份文档的第 12 行”。这里只展示引用格式，不是当前真实运行的证据。

  1. 先限制检索范围。CorpusView.grep() 检查文件清单与预算，有 rg 时使用受限搜索，否则使用受限 Python 正则回退；读取前后检查内容。
  2. 再给命中结果附引用。返回匹配和上下文的 evidence_ref；若结果截断，还可能给出 next_cursor。看见部分结果，不等于检索了全部内容。
  3. 最后核对模型声明。引用需要在交互记录中实际出现，并能在活动快照中解析到有效文档和行；Report 声明只能引用 report 证据。

在没有命中研究缓存的路径上，Report 阶段至少需要一次检索，再通过 complete_report_analysis 完成分析。研究缓存按 snapshot_id 区分，不能仅凭候选名称复用任意旧分析。

来源可靠，不自动等于结论可靠某一行确实写了“平均布线占比 70%”，只能证明这个数字来自哪里；它本身不能证明“所有路径都受布线主导”，也不能证明某个优化必然有效。

源码：corpus.py · L100；corpus.py · L359；stages.py · L912；stages.py · L1190。行号对应本次本地源码。

07默认路径：Report 之后怎样选择

阅读项目时要把“支持的功能”和“当前启用的配置”区分开。当前 config.yaml 启用了 ReAct 流程，但设置了 knowledge_stage_enabled: false，因此独立的 Knowledge 分类阶段默认跳过。

记住：这是当前配置路径；打开 Knowledge 开关后会增加分类研究。

如果打开 Knowledge 阶段呢

它读取批准的 operator_taxonomy.yaml 分类知识，通过受限的 grep_knowledge 支持分类。不要因为源码中还存在旧式案例匹配，就认为当前公共知识检索会开放全部历史案例或任意项目文件。

动作菜单不是模型写出来的

收集函数在具备 operator_mining_candidate 时，就可以收集操作证据并准备 _authorized_action_menu；失败时也可能构建保留合格辅助动作的降级菜单。所以“先研究，再决策”描述的是阶段使用顺序，不表示所有菜单条目都由分析结束后才生成。

staged_decide() 在研究后进入 select_from_action_menu()。分析理由作为 reasoning_evidence_only 留存：它解释选择，但执行权限仍来自菜单和后续校验。

08第五步：从菜单条目到绑定后的动作

可以把菜单理解为本轮可用的“操作卡片”：目标、参数和适用条件已经由程序整理。模型负责从可见卡片中选择，并给出理由。

记住：完整菜单中的审计记录，不等于模型都能选择。

记住：理由可以解释动作；任意改写参数会破坏精确绑定。

先检查资格，再呈现选择

build_action_menu() 基于当前 seed 的工具证据和同次运行中的证明绑定构建菜单。不同动作的资格要求不同：部分算术变换需要提名、证明摘要和特定后端准入，不能把这些条件笼统套用到所有技能上。

公开决策视图还有一层投影：若存在合格的修改类动作，优先呈现修改通道，探查动作被延后，退出项也不在这个通道中展示；否则呈现排名靠前的两个探查及保存退出等哨兵条目。被阻止的条目可留在内部审计或报告里，公开决策侧看到的是阻止原因摘要。

选择 ID，不是重新拼装操作

select_action_menu_entry() 先验证菜单与当前 seed 哈希一致，再查找被选中的合格条目，复制其中保存的操作。staged_decision_binding_error() 进一步检查候选、观测、菜单摘要和 seed 身份，并比较动作及参数是否仍与查表结果完全相同。

一个反例就能理解边界菜单中的卡片绑定了目标 A。即使模型的理由写得很好，也不能把实际执行参数换成目标 B：参数不再等于精确查表结果，会被判为绑定错误。切换候选之后，也不能沿用未经重新校验的旧菜单。

到这里我们只走到了“选出并绑定动作”。它是否带来改善，还要回到第 1 天的技能执行、集中测量与候选评估闭环。

源码：action_menu.py · L600；action_menu.py · L949；stages.py · L74；action_menu.py · L2062；agent.py · L2212。行号对应本次本地源码。

09动手练习与自测

建议分三段完成：20 分钟复算特征，20 分钟追踪证据身份，15 分钟解释动作边界。加上前文阅读，总计约 80–100 分钟。

练习 A：运行本课的小算例

在仓库根目录的 PowerShell 中粘贴下面整段命令。它只调用纯 Python 解析和特征函数，不需要启动 Vivado/RapidWright；-B 避免产生 Python 字节码缓存。

@'
from FDAgents.parsers import parse_utilization_report
from FDAgents.features import extract_features

raw = "| CLB LUTs | 1,200 | 0 | 4,800 | 25.00 |"
analysis = {
    "baseline_wns": -1.0,
    "clock_period": 5.0,
    "utilization": parse_utilization_report(raw),
    "timing_profile": {
        "path_count": 4,
        "route_dominated_paths": 3,
        "avg_route_pct": 70.0,
        "logic_histogram": {"LUT6": 6, "FDRE": 2},
        "logic_levels": {"max": 8, "avg": 5.0},
    },
}
f = extract_features(analysis)
print(f"closure={f.closure_ratio:.2f}; period={f.achieved_period_ns:.2f} ns")
print(f"fmax={f.baseline_fmax_mhz:.2f} MHz; LUTs={f.lut_count}")
print(f"route_ratio={f.route_dominated_ratio:.2f}; avg_route={f.avg_route_pct:.1f}%")
print(f"lut_stage_ratio={f.critical_lut_stage_ratio:.2f}")
missing = extract_features({"baseline_wns": -1.0, "clock_period": 5.0})
print(f"missing_profile_route_ratio={missing.route_dominated_ratio:.1f}")
'@ | python -B -

本例数据为教学构造；验证的是仓库函数的计算行为，不是 FPGA 优化实验。

预期输出：

closure=-0.20; period=6.00 ns
fmax=166.67 MHz; LUTs=1200
route_ratio=0.75; avg_route=70.0%
lut_stage_ratio=0.75
missing_profile_route_ratio=0.0
  1. 只改周期。把 clock_period 改为 10，保留 WNS −1。应得到 closure −0.10、推导周期 11 ns 和 Fmax 90.91 MHz。解释为何相对差距变小，频率数值却更低。
  2. 只改分类数量。把 route_dominated_paths 从 3 改为 2，保留平均值。观察 route_ratio 变为 0.50，理解两个指标在函数中是分别读取的；真实报告仍需由同一组路径统计得到。
  3. 对比缺失。读最后一行的 0.0，指出缺少的不是“好结果”，而是 profile 观测本身。

合上正文，回答五个问题

平均布线占比 70%，为什么布线主导比例可以是 75%？

前者平均每条路径的布线占比，后者统计超过分类阈值的路径数量。本例 4 条路径中有 3 条达到 65% 阈值，因此比例为 3/4。

route_dominated_ratio 为 0，说明没有布线瓶颈吗？

不能直接下结论。path_count 不大于 0 时函数也返回 0；要结合采样数量、profile 内容和遥测可用性区分实测零与缺失回退。

文档名和行号相同，能把候选 A 的引用直接用于 B 吗？

不能仅凭名字复用。引用需要在活动快照和本轮交互记录中验证；快照还绑定候选、DCP 内容哈希与观测轮次。

当前默认配置一定会执行 Knowledge 分类吗？

不会。knowledge_stage_enabled 当前为 false；启用后，知识语料边界也限定为批准的分类文档，而非任意历史案例。

模型理由很充分，能改动卡片中的目标参数吗？

不能。选择通过条目 ID 精确查表，执行参数必须保持与保存的动作一致，并通过当前 seed、菜单与观测绑定检查。
