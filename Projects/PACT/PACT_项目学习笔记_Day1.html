DAY 01   /   理解项目的整体结构

从一份已布线 DCP 出发

读懂 PACT 的输入、双后端、候选搜索与验证闭环。今天的目标是建立全局心智模型，并能沿源码解释一轮优化怎样发生。

阅读约 75–100 分钟主线：DCP → 证据 → 动作 → 验证适合首次接触项目

01项目一句话

PACT（Post-route Agentic Checkpoint Tuning）面向已经完成实现和布线的 AMD FPGA 设计检查点，在给定时间、费用和合法性约束下，寻找更高的可用 Fmax，并导出可验证的 DCP。

输入是什么

Vivado Design Checkpoint，扩展名 .dcp；包含可供工具重新打开的设计状态。评测从原始检查点开始。

优化什么

通过受约束的物理优化、布局/布线局部操作与经证明的算子变换生成候选；以重新测得的时序为准。

最终交付什么

优化后的 DCP、运行记录与验证证据。严格提交模式需要最终等价验证通过，否则回退原始 DCP。

今天先记住三个角色LLM / 决策层提出“试什么”；Vivado 与 RapidWright 后端执行“怎么看、怎么改”；Python 编排层负责时间预算、检查点身份、测量、合法性和回退。

04第一天讲解：四个必须理解的概念

1. DCP 是搜索状态的载体

PACT 不从 HDL 重新综合开始。输入是已有物理实现的检查点；每个动作从某个已保存的“种子候选”出发，输出新的 DCP。candidate_graph.py 用节点记录父候选、文件路径、SHA-256、测量结果和搜索状态。这样可以分叉尝试，也可以在坏操作后重新打开可靠种子。

记住：每个候选都记录“从哪份设计改来”，形成父子关系。

记住：两个候选分别测量比较；它们不必按 A → B 的顺序执行。

2. WNS 和 Fmax 的关系

WNS 是最差建立时间裕量（ns）。项目用 Fmax = 1000 / (clock_period_ns − WNS_ns) 算候选可达到的 MHz。举例：时钟周期 10 ns、WNS 为 −2 ns，得到约 83.33 MHz；WNS 提升为 −1 ns，则约 90.91 MHz。这个值必须建立在相同目标时钟与时序约束之上。

别只看 WNS 一个数measure_candidate() 重新打开候选 DCP，并检查报告是否完整、放置/布线是否合格、hold 与 pulse-width 是否合格、时钟与 timing XDC 是否保持一致。只有满足门槛的候选才有资格进入 beam。

3. “技能”是有边界的动作接口

SkillResult / SkillOutput 规定技能如何交回候选 DCP、摘要和证据。phys_opt 是一个容易理解的入口：选择固定 Vivado phys_opt_design 预设，执行后保存候选。其他技能包括局部重布线、LUT pin swap、pblock、硬宏移动、算子重写等。技能报告是过程证据；最终成绩仍以独立测量为准。

4. 搜索合格、功能等价、竞赛得分是三层判断

候选图看集中测量与搜索收益；严格提交模式进一步对原始 DCP 与最佳候选运行结构/仿真验证并绑定 SHA-256。submission.py 在发布优化输出前保存验证证据，失败时发布原始 DCP。scoring.py 的竞赛分数还考虑运行时间与 LLM 成本：max(0, ΔFmax × (1 − 0.1×成本美元 − 0.1×耗时秒/3600))，验证失败则为 0。该公式解释了为什么“可用提升”比单次漂亮的报告更重要。

05源码阅读路线（按因果顺序）

  1. 先找入口。读 Makefile 的 run_test / run_optimizer，再看 agent.py 的 main() 和 run()。确认 CLI 参数怎样变成运行预算、输出路径与模式。
  2. 看两个后端怎么启动。从 MCPClient.start_servers() 追到 VivadoMCP、RapidWrightMCP。前者给出权威 Vivado 报告，后者擅长设计结构、物理数据与局部 ECO。
  3. 看 root 怎样建立。在 run() 搜索 root_measurement、collect_current_design、record_telemetry_epoch。原始 DCP 也必须先通过测量，才能成为搜索起点。
  4. 看决策怎么落到动作。读 StageRunner、action_menu.py、capabilities.py。注意默认配置启用 staged ReAct；旧式 analyze()/decide() 路径仍在代码中，不能把它当唯一当前流程。
  5. 看候选如何晋级。从 measure_candidate() 到 commit_measured_action()，再到 candidate_graph.py 的 promote()。核对失败、无提升和提升三种结果怎样记入 memory.py。
  6. 最后看导出。查 run() 尾部与 finalize_submission()。常规运行会复制当前 best；--submission 要求严格证据并可能回退 root。
推荐的第一条追踪命令
rg -n "async def run|async def collect_current_design|def commit_measured_action|async def measure_candidate|async def finalize_submission" FDAgents
这条命令会列出主链的几个“接力点”；随后按上面的顺序打开函数即可。

06第一天动手练习

今天建议只做源码级练习。当前目录里的评测 .dcp 文件约 132–134 字节，表现为 Git LFS 指针；运行时还依赖 Linux 风格的 Makefile 环境、Vivado、Java 与 RapidWright，因此不要把未执行端到端流程误写成优化成功。

练习操作验收标准
10 分钟 · 入口定位 main() 中 --no-llm、--submission、--resume 与 --time-limit。能说出“无 LLM”“严格提交”“续跑”是不同开关。
15 分钟 · 量化读 calculate_fmax()，手算 10 ns/−2 ns 与 10 ns/−1 ns 两例。分别得到 83.33 和 90.91 MHz，并解释负 WNS 改善为何提高 Fmax。
20 分钟 · 验证列出 measure_candidate() 的 eligible_for_beam 条件，再查严格提交的 _strict_pass()。能说明集中测量与最终功能等价验证分属不同阶段。
15 分钟 · 追踪选 phys_opt，从技能返回值跟到集中测量、候选图提交。画出自己的 5 节点调用草图，并指出谁给出最终 Fmax。
自测 1：某技能声称 WNS 增加 0.3 ns，可以立即晋级吗？

不可以。必须重新打开输出 DCP 做集中测量，检查报告完整、约束不变、放置/布线和 hold/pulse 合格，并与当前 best 的 Fmax 门槛比较。

自测 2：候选通过集中测量，就等于严格提交成功吗？

不等于。严格提交还会对原始与候选 DCP 运行独立结构/仿真验证并核对证据和文件哈希；失败会回退原始 DCP。

自测 3：为什么每个候选要保留父节点与 SHA-256？

父节点描述动作从哪份设计继续，SHA-256 绑定磁盘上的具体字节。两者有助于恢复、分叉搜索和验证输出与候选图的一致性。
