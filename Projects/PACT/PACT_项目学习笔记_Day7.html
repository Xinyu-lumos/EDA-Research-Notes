01先分清四种证据

第 6 天看到的是某些动作实施前的语义证明。来到收官阶段，要把“动作可执行”“候选可测量”“提交可验证”“论文结果可复现”分开。它们所覆盖的范围不同，不能用后一层的标签去代替前一层实际检查。

候选测量

重新打开规范保存的 DCP，获取时序和物理合法性，用于搜索排序。

严格提交

绑定原始与候选文件身份，结构检查及功能仿真均通过才导出候选。

实验复现

对齐输入、约束、预算、工具、验证与聚合规则，保存逐设计记录。

读图：每层有自己的对象和问题。箭头表示证据要求逐步扩大，并不表示一次运行自动完成论文级复现。

源码：measurement.py · L145；submission.py · L106；README.zh_CN.md · L147。

02搜索阶段：先测可用，再比快慢

measure_candidate() 的输入是一份明确的候选 DCP。它重开该检查点后，查询指定竞赛时钟、时序总结、路由状态与未布局原语数；不使用技能返回的旧 WNS 或缓存的 live-design 数值。缺失关键字段时，measurement_complete 为假，缺失值不会被当成 0。

读图：参考 DCP 对比属于明确传参的分支；读取到一个布尔字段，不足以推断每条调用路径都执行了双文件对比。

候选有完整观测、布局/布线/hold/pulse-width 合法、约束身份满足该次调用的要求，并可计算 Fmax 时，eligible_for_beam 才可能为真。这是搜索资格，并不代表已成为最佳、更不代表最终功能验证通过。部分特殊动作先用集中 Fmax 准入，只有超过种子阈值才花费严格验证预算。

源码：measurement.py · L19、L145、L266；agent.py · L9573。

03最终提交：原始文件先占住输出位

在 --submission 模式，主循环结束后调用 finalize_submission()。它先核对原始检查点身份，并把它复制到输出路径，记为 identity_committed。这样后续候选验证失败或超时，输出仍有受检的原始文件可回退。

读图：进度圆点是状态顺序，不表示自动成功。主路径最终输出的候选内容还要与已验证候选哈希一致。

候选必须属于当前运行的候选目录，大小与 SHA-256 要匹配候选图记录，且有集中测量资格和布局合法性。程序又把 root 与 candidate 复制到一次性的验证目录，限制验证耗时，再保存报告身份。若选中的就是 root，直接记录 fallback_committed；若候选任何关口失败，也会重新复制 root，并写明回退原因。

读图：fallback_committed 表示输出绑定原始设计，不代表优化候选通过了严格验证。

源码：Makefile · L277、L316；agent.py · L10366；submission.py · L106、L140、L263。

04严格验证究竟验证了什么

最终提交的 worker 调用 DCPValidator：第一阶段做结构兼容检查，第二阶段导出仿真模型并做 XSim 功能比较。_strict_pass() 还要求报告绑定原始与候选的哈希和大小、两阶段通过、仿真没有跳过、无基础设施故障、子进程退出码为 0。只有“结构通过”不足以授权优化输出。

读图：四行是合取条件；缺一项便回退到 root。严格模式拒绝“仿真被跳过但结构通过”的情况。

make validate 是独立比较工具，能够报告 PASSED、FAILED 或 INFRASTRUCTURE FAILURE；普通比较中可能出现“仅结构通过”状态。最终提交门使用更严格的接受条件。这里的功能检查是有限向量的仿真比较，不等价于完整形式等价证明，也不能替代器件级 signoff。

证据边界严格提交证明“当前两份哈希绑定的文件通过代码定义的两阶段门”。它没有声称所有可能输入序列都等价，也没有生成论文 35 设计的实验结论。

源码：submission.py · L90、L197；submission_worker.py · L35、L124；validate_dcps.py · L2896；README.zh_CN.md · L128。

05基准素材：输入清单不等于结果包

benchmarks/MANIFEST.csv 有 35 条原始 DCP 条目，划分为 27 个开发设计与 8 个留出设计；SHA256SUMS 用于校验输入文件。DCP 通过 Git LFS 管理，要先实体化并校验，不能把几百字节的 LFS 指针当成可运行检查点。

读图：几何平均的每个设计是一项；面积资源多寡不改变该设计在算式里的项数。

仓库还提供 DATuner 和 Codex Agent 的运行器、参考结果表与部分核对脚本。仓库说明也明确：当前快照缺少完整的逐设计原始结果、统一 signoff 与重画全部论文图表所需的全套材料，不能据此声称论文结果已完整复现。参考 CSV 可以复算其中的汇总公式，但那只是重算给定参考表，不是重跑基准。

06怎样做有解释力的对照实验

一次实验至少要把“输入与约束”“预算与工具”“输出的独立验证”“统计规则”固定下来。PACT 的 make run_optimizer 进入提交模式；make run_test 走无 LLM 的回退路径。它们的用途不同，记录表必须写清楚方法、模型、配置和运行模式。

读图：这是实验记录的四个坐标，不是 PACT 内部执行流程。不同方法的预算口径应明确列出，不能默默视为相同。

例如 DATuner 文档按设计配置 8、12 或 15 次 trial，每次最多 1,200 秒，并明确说明它没有受 PACT 每设计一小时 wall-clock 上限约束；Codex Agent 文档给出的设置则含模型、reasoning effort、一小时上限及独立输出验证。比较质量可以按论文口径，比较时间时必须注明这种预算差异。

最小逐设计记录设计与 split、输入 SHA-256、工具/模型/配置、预算、开始结束时间、输出 SHA-256、重开与布线/时序/功能状态、原始与最终 Fmax、token 与成本、失败类别、日志路径。

源码/资料：Makefile · L277、L321；DATuner README · L19；Codex Agent README · L28、L61；README.zh_CN.md · L158、L169。

07从逐设计结果到汇总数字

基线汇总脚本对每个设计计算 max(1.0, achieved / original)，即未超过原始 Fmax 的方法按 1.0 计，再对同一 split 的比例取几何平均，最后转成百分比改善。此规则会把退步截到 1.0；因此原始逐设计结果仍要保存，不能只存最终百分比。

读图：仅演示聚合公式。条长表示归一化值，不对应真实 DCP 测量或论文中的任何设计。

要复现论文汇总，必须从通过统一 signoff 的逐设计表重新算开发集、留出集和全集；还需要原始日志和两幅图的绘图流程。当前仓库能读到参考表及若干基线汇总脚本，却不足以独立重建全部论文结果。把“源码可运行”“单设计功能跑通”“参考表可重算”“论文结果完整复现”写成四种不同结论。

源码/资料：Codex 汇总脚本 · L16；DATuner 汇总脚本 · L15；README.zh_CN.md · L147。

08动手练习与自测

下面只调用 Python 纯函数，人工构造“报告字段”和“两条基准记录”，不启动 Vivado，不读 DCP。请在仓库根目录的 PowerShell 运行；-B 避免写字节码缓存。

@'
from FDAgents.submission import ArtifactIdentity, _strict_pass
from baselines.codex_agent.summarize_results import normalized_score, geometric_mean

root = ArtifactIdentity("root.dcp", 100, "a" * 64)
child = ArtifactIdentity("child.dcp", 120, "b" * 64)
report = {
    "schema_version": 1, "strict_mode": True,
    "root_sha256": root.sha256, "root_size_bytes": root.size_bytes,
    "candidate_sha256": child.sha256,
    "candidate_size_bytes": child.size_bytes,
    "phase1_passed": True, "phase2_passed": True,
    "phase2_skipped": False, "infrastructure_failure": False,
    "process_exit_code": 0,
}
print(_strict_pass(report, root, child))
report["phase2_skipped"] = True
print(_strict_pass(report, root, child))

rows = [
    {"example": "A", "original_fmax_mhz": "100", "codex_fmax_mhz": "110"},
    {"example": "B", "original_fmax_mhz": "200", "codex_fmax_mhz": "180"},
]
values = [normalized_score(row) for row in rows]
print(values, round((geometric_mean(values) - 1) * 100, 2))
'@ | python -B -

复现实验清单 · 有工具时再执行

  1. 准备输入。从 Git LFS 实体化 DCP，运行 sha256sum -c SHA256SUMS，保存 35 行清单与目标时钟。
  2. 固定环境。记录 Vivado 版本、RapidWright 版本、Python 锁文件、许可证、模型/endpoint、配置与预算；开发/留出 split 不改。
  3. 逐方法运行。每方法从相同原始 DCP 开始；保留各自真实预算设置与完整日志。PACT 可从 make run_optimizer DCP=... 入手。
  4. 独立 signoff。重新打开输出，检查布线、setup/hold/pulse-width/min-period、时钟与 I/O/约束身份，并做适用的功能比较；明确失败或设施故障。
  5. 重新聚合。保存逐设计机器可读表，按 train/test/all 三组计算；重画图 1、图 2 与表 II，核对论文口径。

读图：高一阶结论要补齐对应的原始记录与统一方法；完成前一阶不能自动声明后一阶。

合上正文，回答六个问题

eligible_for_beam=True 能说明候选功能等价吗？

不能。它说明当前集中测量完整、物理和约束条件满足当前调用要求，可参与搜索；严格功能验证是另一层。

提交一开始为什么就复制原始 DCP 到输出？

先建立可回退的输出身份。候选不通过严格门时，最终 manifest 为 fallback_committed，输出绑定原始设计。

结构检查通过、仿真跳过，可提交优化候选吗？

不能。最终 _strict_pass 明确要求 phase2_passed=True 且 phase2_skipped=False。

有限向量 XSim 通过可以称为形式等价吗？

不能。它是有范围的功能仿真比较；可报告具体协议与向量数，但不应扩展为所有可能输入的证明。

为什么不能只比较 PACT 与 DATuner 的最终 Fmax 和时间？

还需对齐原始输入、约束、验证、split 和记录预算口径。DATuner 的 trial 预算与 PACT 一小时上限不同，时间结论应注明。

用参考 CSV 算出 +15.14% 等于重跑论文了吗？

不等于。它只说明给定表按公式能聚合；完整复现还需可获得的输入、各方法原始日志、统一 signoff、逐设计表及图表脚本。

七天课程的最后一问面对任何“提升了 X%”的说法，先找输入 DCP 与约束身份，再找输出验证报告，最后找逐设计表与聚合公式。能追到文件和规则，数字才有可审查的含义。
